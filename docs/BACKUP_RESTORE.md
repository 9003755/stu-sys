# 备份、恢复与账号权限交接手册

核对日期：2026-10-12。此文是执行手册与验收标准；本次没有创建生产备份、恢复数据库、下载学员文件或验证现有备份可用性。仓库没有可证明最近备份时间、保留周期、恢复演练结果的清单，所以不能声称“数据已备份”或“可保证零丢失恢复”。

## 1. 什么需要独立保存

| 资产 | 必须保留的内容 | Git 是否足够 |
|---|---|---|
| 应用源码 | 指定分支、commit、lockfile、public 模板、文档、SQL、Edge Function 源码 | 可保存；必须确认已 push |
| 数据库业务数据 | 档案、班级、报名、角色、二维码配置、两份资料的关联与路径、线上额外表 | 不足；SQL 迁移不含真实记录 |
| Auth 数据 | 用户 UUID、身份关联、所需账号状态；平台支持方式下的密码哈希/身份数据 | 不足；仅导出邮箱再注册会改变 UUID，破坏外键关联 |
| Storage | 两桶实际对象字节、完整对象路径、大小、校验和、内容类型及可见性配置 | 不足；DB 中 `storage.objects` 是元数据，不是图片 |
| 数据库配置 | 当前 schema、RPC 定义/owner/授权、RLS、触发器、外键、索引、扩展、实际迁移台账 | 历史迁移不保证等于现网 |
| Auth 配置 | Site URL、允许 redirect URL、提供商、邮箱/SMTP、注册与邮箱验证策略、限流等 | 控制台设置需独立记录 |
| Edge Functions | 线上 slug、部署版本、JWT 设置、secrets 名称与安全保管位置 | 源码有；部署配置/密钥值不在仓库 |
| 定时邮件 | cron 名称/表达式/时区/目标 slug、Resend 发件身份、额度和收件人 | 不应把含 Authorization 的 command 公开归档 |
| Netlify | site ID、生产分支、构建配置、环境变量、域名/证书/DNS、部署记录 | 源码不包含平台所有设置 |
| 组织访问权 | GitHub、Netlify、Supabase、Resend、域名/DNS、备份存储的成员权限和恢复方式 | 需平台邀请/组织权限交接 |

本系统上传含身份和健康相关资料。备份文件、Auth dump、原始日志与二维码 token 按生产数据管理：加密保存、限制成员访问、不进入 Git 或公开网盘。文档仅存资产清单、备份编号和安全存储引用。

## 2. 首次建立备份流程

1. 在 Supabase Dashboard 的数据库备份页面核对当前计划是否提供自动备份/PITR、最近成功时间、覆盖范围与保留期限。记录实际页面结果；不能从历史 Free/Pro 容量数字推断当前权益。
2. 由负责人确定恢复点目标（最多容忍丢失多久的数据）和恢复时间目标。建议至少每日检查备份、每次数据/权限迁移前设置恢复点；这只是建议，不代表已配置自动任务。
3. 确认备份目标存储和加密方式，与生产项目分开控制访问。先用小规模假数据进行恢复演练，再决定可用方案。
4. 以平台支持的方式保存 DB（包括业务数据和必要的 Auth 数据）及当前配置，再通过 Storage API/受控导出工具备份两个桶的实际对象。不要直接修改 `storage.objects` 来导出或恢复文件。
5. 为文件备份建立受限 manifest：`bucket/path`、字节数、SHA-256、content-type、备份时间/版本。至少同时记录两桶对象总数和总字节数。名单及路径可能含个人信息，manifest 也不得公开。
6. 最好在短暂的受控暂停写入窗口内形成一致恢复点。若不中断上传，DB 与 Storage 备份并非同一原子快照：记录开始/结束时间，并在恢复副本中核对新增、覆盖、删除对象；必要时再次补同步。仅有“备份任务成功”不等于一致性通过。
7. 将备份编号、时间范围、范围、校验结果、恢复演练结果和负责人登记到受限台账。没有通过恢复演练的备份标记为“未验证”，不能作为已保障恢复的证据。

用户没有要求生产资料自动到期删除，本次也没有设置任何自动删除或备份清理。备份保留周期、版本数、成本和负责人需要与机构负责人另行落实，不能默认销毁旧恢复点。

### 受控逻辑导出的备选方式

优先使用适配当前 Supabase 计划的官方恢复功能。若需自管逻辑备份，应先参考 [数据库备份说明](https://supabase.com/docs/guides/platform/backups) 与 [项目迁移说明](https://supabase.com/docs/guides/platform/migrating-within-supabase)，验证工具版本和托管 schema 的限制。

下面只描述 Postgres 运维工具的一种导出方式，**本次未执行，也不是一键恢复脚本**。使用与服务器主版本兼容的 `pg_dump`/`pg_restore`。连接参数应由安全凭据管理工具提供到进程环境，或受限 `PGPASSFILE`；不要把 connection string/密码粘贴进命令历史。输出目录在仓库之外，由运维人员先创建并控制 ACL。

```powershell
# PGHOST / PGPORT / PGDATABASE / PGUSER 与 PGPASSFILE 由受控环境提供。
# 请先在隔离项目验证连接、导出范围及恢复流程。
pg_dump --format=custom --schema=public --schema=auth --schema=storage --file='D:\secure-backups\stu-system\database.dump'
pg_restore --list 'D:\secure-backups\stu-system\database.dump'
Get-FileHash -Algorithm SHA256 'D:\secure-backups\stu-system\database.dump'
```

此命令只选择三套 schema，不代表导出了整个项目：Cron、扩展/角色、平台设置、Edge Functions、密钥及文件字节必须另行保存。`pg_dump` 返回码必须为 0，审阅 stderr，并在目录清单中核对期望表、函数、策略、约束和数据。不得用 `--exclude-schema=auth` 等选项后仍标记为完整账号备份。

Auth/Storage 的托管结构、owner 和角色依赖可能不允许直接导入另一 Supabase 项目。不要对生产运行 `pg_restore --clean`。恢复方案必须针对平台版本审查 TOC 和依赖，在隔离目标上采用官方支持的恢复流程；必要时仅恢复经审查的数据到平台已经创建好的结构。导出成功不证明恢复路径已成立。

## 3. Storage 对象备份/恢复要求

应从 Storage 服务读取对象实际内容，并分桶保留原始 key。任何实施脚本至少需要：分页列举、递归目录/前缀、限制并发、网络重试、校验 HTTP 错误、下载后计算校验和、成功/失败清单，以及基于 manifest 跳过已验证文件。不能只列出第一页，也不能只备份本次 ZIP 中的已匹配资料。

`class-submission-documents` 包含待核对姓名的资料，也属于备份范围。管理页全班 ZIP 是业务导出，通常只包含已匹配报名的资料，且不保留所有数据库关联和原始 Storage key，不能用它替代系统备份。

恢复时通过 Storage API 上传到正确 bucket/key，保持 JPEG 内容类型；对已存在对象先比对，不默认覆盖。上传后重新校验文件字节、对象数量和 DB 引用。私有桶继续私有；旧 signed URL 不需要恢复，应由系统重新签发。新项目 URL 不同则需要审查 `profiles` 的绝对 public URL，保留 UUID 仍不能自动修复旧域名链接。

仓库未提供已验证的全桶备份脚本，本手册不会把未运行的伪脚本当作现有能力。接手实施时，应将脚本纳入仓库但将备份内容保存在受限存储，并补充一次完整演练记录。

## 4. 恢复执行顺序

1. 明确故障范围、最后可信时间、是否还在写入。指定操作负责人，保护故障现场日志/当前备份，不以新的备份覆盖唯一旧恢复点。
2. 优先建立隔离目标：独立 Supabase 项目、测试 Netlify 站点或预览、测试收件人。禁用生产 cron 和对外邮件，防止恢复副本触发真实通知。
3. 选择已验证备份。平台提供原项目恢复时，先确认平台覆盖范围及窗口；跨项目逻辑恢复要检查版本、扩展、托管 schema、UUID/身份关联，不运行历史迁移文件全量重放。
4. 恢复数据库及 Auth 关联，重新检查结构、外键、RPC/RLS/权限与 schema hash。恢复 Auth 数据不等于旧会话一定有效；JWT key/域名变化时安排重新登录。
5. 恢复两桶实际文件并校验 manifest。对引用缺失文件、无 DB 引用文件、跨班链接、`matched` 却无 enrollment 的记录建立清单，不自动删除或强行修正。
6. 恢复 Edge Function 的正确 slug/JWT 配置及服务端 secrets、Auth redirect/邮件配置。新项目 anon/service keys 会变化；更新前端环境后重新构建，不能修改生成后的 JS 来替换凭据。
7. 在隔离环境按下一节验收；通过后记录获批恢复方案与切换窗口。生产切换涉及真实数据，应在方案具体可审查后由负责人批准；不能在演练中悄悄替换生产。
8. 切换后执行线上只读/非破坏性烟测，核查日志和用户反馈，再按原业务设置启用 cron。记录恢复点、完成时间、数据差异与处理结果。

## 5. 恢复验收标准

| 检查 | 通过条件 |
|---|---|
| 结构 | 核心表/字段/外键/索引/RLS/RPC 与选定恢复点一致；差异有批准记录 |
| 数据 | 各表行数与恢复点清单可对账；无意外孤儿/跨班关联；Auth UUID 保持对应 |
| 图片 | 两桶 manifest 文件数、大小、校验和一致；抽样打开图片，DB 引用可解析 |
| 权限 | 学员只能访问允许数据；普通管理员不能获取其他管理员私有资料；匿名不能执行运维 RPC |
| 登录 | 学员/普通管理员/超级管理员均可正常登录、退出、刷新；异常不会无限加载 |
| 报名 | 假资料账号完成报名、三张图片上传及管理员查询 |
| 资料收集 | 测试班二维码扫码、两张独立图片、四角确认、匹配/待核对、替换、纠正姓名正常 |
| 下载 | 单份、完整 ZIP、弱网重试/续传和目录结构通过；参见 ZIP 专项文档 |
| 删除 | 仅隔离环境专用假账号验证单删/批删，确认影响范围与文件处理；不以真实学员作测试 |
| 邮件 | 获授权后向测试收件人验证函数；生产 endpoint/计划/额度核对后才启用任务 |
| 切换 | 前端环境指向正确项目；旧二维码和图片 URL 的有效性有明确处置 |

“接手者能运行前端”与“可以从灾难恢复完整业务”是两种验收，不能互相替代。本次没有进行本节的生产恢复演练。
